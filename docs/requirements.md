# AgentRPA 产品需求规格说明

## 1. 文档目的

本文档用于定义 AgentRPA 的业务范围、功能边界、角色、业务流程、数据模型、权限、安全、异常及后续开发验收标准。

需求描述统一采用：

> **角色 + 场景 + 页面/入口 + 操作 + 系统结果 + 数据规则 + 权限规则 + 异常规则**

---

## 2. 用户角色

### 2.1 平台超级管理员

负责平台级配置、组织、城市、系统、功能、权限和安全策略。

### 2.2 系统管理员

负责被授权城市和业务系统的配置、Workflow 管理以及运行维护。

### 2.3 业务管理员

负责具体业务功能配置、数据模板、任务查看和业务结果处理。

### 2.4 普通业务用户

通过自然语言发起任务，并查看自己有权限范围内的任务和结果。

### 2.5 RPA 运维人员

负责执行节点、浏览器环境、Workflow 版本和异常运行维护。

---

## 3. 城市管理

### 3.1 城市新增

管理员进入城市管理页面，填写城市名称、行政区划代码、编码、状态和备注后提交，系统创建城市。

**规则**：城市编码唯一；停用城市后不能创建新任务，但历史数据保留。

### 3.2 城市编辑

管理员可以修改名称、备注和状态。城市编码原则上创建后不可修改，以保证历史数据关联稳定。

### 3.3 城市停用

停用前系统应提示当前关联的业务系统、Workflow 和运行任务。已运行任务默认允许完成或由管理员取消，不应直接删除历史记录。

---

## 4. 业务系统管理

### 4.1 系统注册

管理员选择城市后创建业务系统，配置名称、编码、访问地址、系统类型、登录方式、描述和状态。

**规则**：同一城市下系统编码唯一；不同城市允许存在相同系统编码。

### 4.2 系统配置

支持：

- 基础 URL
- 登录入口
- 登录方式
- 浏览器要求
- 超时时间
- 网络代理
- Cookie/Session 策略
- 是否允许人工接管
- 是否启用

### 4.3 系统健康检查

管理员可以主动检查网站入口、DNS/网络连通性、登录页面和关键页面是否可访问。检查结果进入系统运行日志。

---

## 5. 业务功能管理

### 5.1 功能定义

管理员在某个“城市 + 系统”下创建具体业务功能，例如：人员查询、缴费查询、缴费明细、参保信息查询。

功能至少包含：

- 功能名称
- 功能编码
- 描述
- 输入参数
- 输出参数
- Workflow
- 是否允许自然语言调用
- 是否允许批量执行
- 是否允许导出
- 状态

### 5.2 参数定义

参数需要明确：

```text
Name
Code
Type
Required
DefaultValue
Description
Sensitive
ValidationRule
```

支持字符串、数字、日期、日期范围、文件、人员列表等基础类型。

---

## 6. 权限管理

### 6.1 权限范围

权限至少支持：

```text
城市
  → 业务系统
      → 业务功能
          → 操作
```

### 6.2 操作权限

建议标准化为：

- View
- Execute
- Create
- Update
- Delete
- Export
- Configure
- Debug

### 6.3 权限判断

自然语言任务解析得到城市、系统和功能后，必须先执行授权检查。

授权失败：

```text
PermissionDenied
```

任务不得进入 RPA 执行队列。

### 6.4 最小权限原则

默认无权限；必须显式授权。角色可以拥有多个 AccessPolicy，用户可以通过角色获得权限，同时允许特殊用户授权覆盖策略，但不能绕过平台安全策略。

---

## 7. Agent 对话

### 7.1 自然语言任务

用户输入业务目标，Agent 应提取：

- 城市
- 业务系统
- 业务功能
- 操作类型
- 输入数据
- 时间范围
- 人员/业务对象
- 输出格式
- 其他业务参数

### 7.2 意图不明确

当城市、系统或功能无法唯一确定时，Agent 不应猜测执行。应向用户提出最小必要澄清问题。

例如：

> 检测到“社保系统”在北京存在两个可用系统，请选择具体系统。

### 7.3 任务确认

对于高风险、批量修改、申报等操作，应支持二次确认。

查询类低风险任务可以根据管理员策略直接执行。

---

## 8. TaskPlan

Agent 完成理解后生成结构化任务计划：

```json
{
  "cityId": "...",
  "systemId": "...",
  "functionId": "...",
  "action": "Execute",
  "parameters": {},
  "inputFiles": [],
  "outputPolicy": {},
  "workflowId": "...",
  "workflowVersion": "..."
}
```

TaskPlan 必须是可审计、可重放的结构化数据，不能只保存自然语言。

---

## 9. RPA Workflow

Workflow 是业务功能对应的确定性自动化流程。

### 9.1 Workflow 内容

```text
Workflow
├── 基础信息
├── 输入参数
├── 前置条件
├── Steps
├── 输出映射
├── 异常处理
├── RetryPolicy
└── Version
```

### 9.2 Step 类型

建议支持：

- OpenPage
- Click
- Input
- Select
- Wait
- WaitForElement
- Extract
- Upload
- Download
- Screenshot
- ExecuteScript
- Condition
- Loop
- CallWorkflow
- HumanIntervention
- Assert
- End

### 9.3 版本管理

Workflow 修改必须产生新版本，不直接覆盖历史版本。

运行中的任务固定 WorkflowVersion，不能因后台发布新版本而改变执行逻辑。

---

## 10. RPA 执行

### 10.1 浏览器

浏览器执行器负责：

- 浏览器生命周期
- 页面导航
- 元素定位
- 鼠标/键盘操作
- iframe
- 弹窗
- Cookie/Session
- 下载/上传
- 截图
- 网络错误处理

### 10.2 执行上下文

每个任务建立独立 ExecutionContext，包括：

```text
TaskId
UserId
AuthorizationContext
BrowserSession
WorkflowVersion
Variables
Artifacts
CancellationToken
```

### 10.3 并发

并发数量由执行节点资源、业务系统限制和管理员策略共同决定。对于同一账号/同一业务系统，可以设置串行锁，避免账号被网站风控。

---

## 11. 批量任务

对于 Excel 人员列表，系统不应将全部数据一次性交给 Agent。

推荐：

```text
Excel
 ↓
Parse
 ↓
Validate
 ↓
Batch
 ↓
Task Items
 ↓
Worker Queue
 ↓
Workflow
```

每个人员作为独立 TaskItem，具备独立状态和重试次数。

这样可以实现：

- 单条失败重试
- 失败项重新执行
- 中途暂停后继续
- 部分成功
- 统计成功率

---

## 12. 人工接管

当 Workflow 遇到验证码、短信、UKey、扫码、人脸或无法自动处理的页面时进入 `WaitingHuman`。

用户完成操作后点击继续，执行器恢复当前 Workflow。

**要求**：人工介入期间不能丢失浏览器 Session、任务变量和当前 Step。

---

## 13. 任务中心

任务中心至少展示：

- 任务编号
- 创建人
- 创建时间
- 城市
- 系统
- 功能
- 状态
- 当前步骤
- 总数量
- 成功数量
- 失败数量
- 重试数量
- 开始时间
- 完成时间
- 耗时

支持：

- 查看
- 暂停
- 恢复
- 取消
- 重试失败项
- 下载结果
- 查看执行日志
- 查看截图

---

## 14. 数据文件

输入支持：

- Excel
- CSV
- TXT
- PDF
- Word
- 图片

文件必须保存元数据并与任务建立关联。敏感文件应根据组织和任务权限控制下载。

输出支持：

- Excel
- CSV
- JSON
- PDF/报告

---

## 15. 凭据中心

支持用户名密码、Token、Cookie、证书、UKey 等类型。

要求：

- 加密存储
- 权限分级
- 脱敏展示
- 禁止写入普通日志
- 任务只获取执行所需的凭据
- 凭据轮换后不影响历史审计记录

---

## 16. 异常与重试

异常分为：

```text
BusinessError
SystemError
NetworkError
BrowserError
AuthenticationError
PermissionError
TimeoutError
DataValidationError
HumanInterventionRequired
```

重试策略支持：

- 最大次数
- 间隔
- 指数退避
- 指定异常可重试
- 指定 Step 可重试

业务错误通常不应无限重试。

---

## 17. 审计

每次任务必须能够追溯：

```text
用户
→ 任务
→ TaskPlan
→ 权限判断
→ WorkflowVersion
→ Step
→ 输入/输出
→ 异常
→ 最终结果
```

敏感字段必须脱敏或只保存不可逆摘要。

---

## 18. 监控

平台应提供：

- 当前运行任务
- 执行节点状态
- Workflow 成功率
- 平均耗时
- 失败率
- 重试率
- 人工介入次数
- 各城市任务量
- 各系统任务量
- 各功能成功率

后续可以增加系统 SLA 和异常趋势分析。

---

## 19. 非功能要求

### 性能

- Agent 任务规划与 RPA 执行解耦。
- 大批量任务采用队列和 Worker。
- 文件处理采用流式/分批方式，避免一次加载超大文件。

### 稳定性

- Worker 崩溃后任务可以恢复。
- 浏览器崩溃后能够重新建立 Session，并根据策略恢复。
- 单条业务失败不能导致整个批次丢失。

### 安全

- RBAC + 资源级授权。
- 敏感数据加密。
- 全量审计。
- Agent 无法绕过 Permission Engine。

---

## 20. 验收示例

### 场景 A：有权限查询

用户拥有：

```text
北京 → 社保 → 缴费查询 → Execute
```

输入：

> 查询人员 Excel 中所有人员 2026 年 8 月缴费情况。

结果：创建任务并进入执行队列。

### 场景 B：无权限

用户只有：

```text
北京 → 社保 → 人员查询 → View
```

但请求：

> 执行缴费申报。

结果：权限拒绝，不启动浏览器。

### 场景 C：需要人工

Workflow 执行到短信验证：

```text
Running
 ↓
WaitingHuman
 ↓
用户完成短信验证
 ↓
Running
 ↓
Completed
```

### 场景 D：批量部分失败

100 人：

```text
成功 96
失败 4
```

系统保留 4 条 TaskItem，可以只重新执行失败项，不重新执行 96 条成功记录。
